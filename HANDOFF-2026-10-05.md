## 2. Reglas de trabajo con este usuario (obligatorias)

1. **No correr NINGÚN comando de PowerShell sin pedir permiso antes**: decir qué comando, por qué y si es solo
   lectura, y esperar el sí. Un sí vale solo para ese comando. Esto incluye `dotnet build`, `dotnet test`,
   `dotnet ef`, `git log`/`git diff` y `sqlcmd`. Preferir siempre las herramientas de lectura (Read, Grep, Glob).
2. **No levantar el servidor** (`dotnet run` / `preview_start`). El usuario lo levanta y verifica en **Edge**.
   Recordar que los `.razor.css` (CSS con ámbito) solo se recompilan en el build: tras cambiar estilos, el usuario
   tiene que reiniciar su servidor.
3. **Calidad exigida** (cita del usuario): *"que no haya hardcodeo innecesario, y que el código siga el Clean
   Architecture que llevamos implementando, más SOLID en caso de que convenga. El código debe quedar pulcro para
   que sea sencillo de leer, seguro, y escalable."*
4. **Plan antes de implementar** cualquier cambio no trivial (modo plan → aprobación). Cuando el usuario pide un
   *double-check*, hacerlo de verdad (releer el código, buscar contraejemplos), y no dar algo por verificado solo
   porque compila.
5. **Un commit por cambio.** El usuario hace los commits él mismo; Claude le entrega el mensaje de commit en
   español (cuerpo sin tildes, como los anteriores: título + "Motivo:" + secciones + "Verificado:").
6. **Licencias:** antes de agregar o actualizar un paquete NuGet, revisar las condiciones reales de su licencia
   (EDEEste es una entidad pública; QuestPDF quedó descartado por eso). La decisión es del usuario.
7. Código, comentarios y textos de la interfaz **en español**. Las páginas son `Foo.razor` + `Foo.razor.cs`
   (CodeBehind, `[Inject]`, sin `@code` en páginas nuevas). Autorización **por permiso**, nunca por rol.
   `AGENTS.md` es la guía del proyecto: leerla primero.

## 7. Memorias relevantes (copiadas, porque no viajan)

- **Multidispositivo:** el usuario alterna dispositivos y sincroniza solo por git (rama `Basics`; la principal es
  `master`). En un dispositivo nuevo:
  - Clave HMAC: `dotnet user-secrets set "Criptografia:ClaveHmac" "<base64 de 32 bytes>" --project
    EDEEste.ControlCajaChica.Presentation`.
    - Generarla con `RandomNumberGenerator.Create().GetBytes(32)`. **No** con `RandomNumberGenerator.Fill` en
      PowerShell 5.1: no hace nada y produce una clave de ceros.
    - Una clave nueva invalida las firmas de datos copiados de otra máquina.
  - Instalar `dotnet-ef` 10.0.11 si falta.
  - Aplicar migraciones: `dotnet ef database update --project EDEEste.ControlCajaChica.Infrastructure
    --startup-project EDEEste.ControlCajaChica.Presentation`.
- **Verificación visual:** el usuario levanta el servidor y revisa en Edge. Una vez que Claude lo levantó, el
  proceso bloqueó un build y el usuario no podía detenerlo.
- **Disciplina de seguridad:** ante un arreglo de seguridad o de CSS con ámbito, no basta con que compile:
  revisar el resultado real (advertencias, CSS compilado, comportamiento) y buscar cómo refutar la hipótesis antes
  de reportarla.
- **Datos de BDD con firma:** nunca corregir una fila firmada (`FondoCajaChica`, `Gasto`, etc.) con un `UPDATE`
  directo, porque queda como manipulada. Si hay que ajustar datos, hacerlo por el camino de la aplicación (en
  septiembre se hizo con un programa de un solo uso que reutilizaba `ApplicationDbContext`, los interceptores y la
  clave real).
- **Bitácora a nombre de "Sistema":** resuelto el 2026-09-11. `AuditoriaInterceptor` (Singleton) pide el usuario
  al `ApplicationDbContext`. Un ámbito de DI creado a mano dentro de un circuito necesita
  `SetAuthenticationState` o el registro queda como "Sistema".
- **Datos de prueba en la LocalDB de este dispositivo** (no reversar sin que el usuario lo pida):
  - 16 gastos de prueba del fondo de `custodio.prueba` (fondo `0F4E8887…`, monto fijo RD$20,000, alerta en 30%).
  - Varias reposiciones de prueba de hoy (`28250032…` y las del recorrido de EnReposicion).
